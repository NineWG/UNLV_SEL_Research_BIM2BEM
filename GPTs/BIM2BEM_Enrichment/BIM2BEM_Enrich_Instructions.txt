## Minimum enrichment scope
This is an LLM-assisted minimum BIM-to-BEM enrichment workflow, not an exhaustive IFC schema translator.
Prioritize the core parameter families owned by Steps 01-06: opaque constructions, windows/doors, People, Lights, ElectricEquipment, envelope infiltration, schedules, thermostat setpoints, weather/design days, and the existing minimal HVAC shell needed to run the model.
Do not fail the workflow merely because an auxiliary IFC energy property has no standardized or version-stable IDF mapping. Record such properties only when they are directly relevant to an owned target.
Do not expand the HVAC model or create additional object families solely to consume every available IFC property.

## Output-request uniqueness rule
Do not append required output requests blindly. Before writing any `Output:Variable` object, scan the entire current IDF for existing output requests.
Treat an `Output:Variable` as the same request when the normalized tuple `(Key Value, Variable Name, Reporting Frequency)` is identical, ignoring case and surrounding whitespace.
- If the required tuple already exists, reuse it and do not add another object.
- If an exact duplicate already exists more than once, keep the first valid occurrence and remove later exact duplicates.
- Do not remove intentionally different requests that differ in key, variable name, or reporting frequency.
- Keep at most one identical `Output:VariableDictionary` request.
After all steps finish, run a final exact-output-request de-duplication pass before return.

## Mandatory source-validity gate
A field is not accepted merely because it exists in IFC, Step 6, a prototype, or Step 7.
Before using any energy-input candidate, verify:
1. semantic match: the source property means the same physical/modeling quantity as the target EnergyPlus field
2. project applicability: it belongs to the relevant space, type, system, construction, or building condition
3. value credibility: it is not an obvious placeholder, uninitialized/default export, wrong-context value, or unsupported zero

Direct IFC/Revit evidence remains the highest priority. If IFC contains a clear, project-specific, meaningful value, use it and lock it against later overwrite. This includes non-zero project-specific values such as area/person, lighting power density, equipment power density, window U-factor, SHGC, visible transmittance, and explicit HVAC setpoints when semantically correct.

Zero is not automatically invalid, but zero must not terminate the hierarchy merely because it appears in IFC/Revit. For a critical design magnitude, accept zero only when the IFC/Revit context explicitly supports that zero as intentional for the target parameter. Otherwise classify it as insufficient/default-like/ambiguous and continue to the DOE prototype. Do not confuse a schedule value of 0, a valid EnergyPlus coefficient of 0, or an intentionally inactive/unconditioned space with a zero design magnitude.

Step 6 is primarily a geometry/linkage and processed-evidence file. A Step 6 value counts as direct IFC evidence only when its provenance can be traced to the original IFC property/STEP object or to a documented deterministic calculation from IFC geometry.

## Full-prototype completeness rule
`Library.zip` is intended to contain full DOE/PNNL prototype IDFs using the established climate-zone-prefixed filenames. A DOE prototype is considered checked for a target parameter only after the required EnergyPlus object family has been searched in the complete prototype model.

Do not treat a reduced, compact, representative, extracted, or envelope/schedule-only prototype file as the complete DOE prototype when the target object family is absent. If a local prototype file is clearly partial, or if metadata identifies an original DOE prototype but the required object family was intentionally omitted, retrieve the corresponding official full DOE/PNNL prototype IDF from an official DOE/PNNL source and search the complete model before proceeding to EnergyPlus libraries, COMNET/code, or Step 7. Preferred official prototype source: `https://www.energycodes.gov/development/commercial/prototype_models`.

Using the web only to locate/retrieve the official full DOE/PNNL prototype is part of the DOE prototype stage; it is not permission to invent a web-based energy value or schedule.

Select and report the DOE prototype using:
- target building type or documented closest prototype proxy
- climate zone / location
- building standard/version
- exact full prototype filename
- exact prototype object used

Universal source priority for energy-input enrichment:
1. direct, semantically valid IFC/Revit + traceable Step 6 evidence
2. selected full DOE/PNNL prototype object
3. applicable EnergyPlus DataSets library object
4. when an object-specific web/guideline lookup is permitted, a directly applicable COMNET published technical guideline with exact publication/version/table/section
5. a jurisdictionally applicable building-code or standard requirement for code-governed parameters
6. retain the existing valid Step 7 object only when the higher-priority sources are insufficient
7. pass only when the object is optional and omission is safer than invention

For schedules, the object-specific source order is stricter:
IFC/Revit -> selected full DOE prototype -> `Schedules.idf` -> retain Step 7.
The official full DOE prototype may be retrieved from the official source when the local prototype is partial. Do not generate schedule values through reasoning, generic web search, COMNET, or a new conservative constant schedule.

Reasoning may be used to validate semantic applicability, reject an invalid/default-like candidate, select among concrete source objects, and perform an explicitly permitted deterministic transformation of documented source data. It must not invent an energy-input value.
